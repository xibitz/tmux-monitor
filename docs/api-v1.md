# API v1 contract

The PRD remains the product contract. This file defines the implemented M0 and SSH slices;
unimplemented connectors never return invented inventory or connection success.
All timestamps use RFC 3339 UTC. All responses under `/api` and `/ws` use
`Cache-Control: no-store`. IDs are opaque. Errors have the form
`{"error":{"code":"forbidden","message":"…","requestId":"…"}}`.
`X-Request-ID` is generated by the server and returned on every response.

| Method and path | Authorization | Request / response |
| --- | --- | --- |
| `GET /healthz` | Local listener | `{"status":"ok","schemaVersion":5}` in current source (migration005 untested); 503 if storage is unavailable |
| `POST /api/v1/auth/login` | Exact configured Origin, rate limited | `{username,password}` → `{user,csrfToken}` and session cookie; generic 401 for invalid credentials |
| `GET /api/v1/me` | Session | `{user:{id,username,isAdmin},csrfToken}` |
| `POST /api/v1/auth/logout` | Session + CSRF | 204; revoke session and expire cookie |
| `GET /api/v1/hosts` | Session, filtered by host permissions | `{hosts:[Host]}` |
| `GET /api/v1/hosts/options` | Admin | `{allowedSSHHosts:[string]}`; sorted exact addresses approved in hub configuration, empty array if none; does not test connections |
| `POST /api/v1/hosts` | Admin + CSRF | `HostInput` → 201 `Host`; creates configuration only |
| `PATCH /api/v1/hosts/{id}` | Admin + CSRF | Full `HostInput` → `Host`; future connector configuration is immutable in this milestone |
| `DELETE /api/v1/hosts/{id}` | Admin + CSRF | 204; deletes profile only, never touches tmux |
| `GET /api/v1/hosts/{id}/ssh` | Admin | SSH configuration metadata: configured, port, host key fingerprint and configuredAt; no key or secret path |
| `POST /api/v1/hosts/{id}/probe` | Admin + CSRF | Run bounded SSH/tmux observation; `{host,inventory}` on success; audit metadata only |
| `GET /api/v1/hosts/{id}/inventory` | `tmux:read` | Fresh SSH snapshot, or last successful snapshot marked stale on failure; 404 for inaccessible/absent hosts |
| `GET /api/v1/audit?limit=50&before=123` | Admin | `{events:[AuditEvent],nextCursor:"…"}`; maximum limit 100 |

Mutations require `Origin` equal to `TMUX_MONITOR_ORIGIN` and
`X-CSRF-Token` from login or `/me`. Login also requires Origin. Cookies are
HttpOnly, SameSite=Strict, Path=/, Secure in production, with a 12-hour expiry.
Production origin must be HTTPS. HTTP and non-Secure cookies require the explicit
local development setting. The server always binds to `127.0.0.1`.
There is no public user registration; use the local bootstrap CLI once.

`HostInput` fields: `label` (1–80 characters), `transport` (`ssh` or `agent`),
`tailnetAddress`, `osUser`, `socketName` (default `default`), `environment`
(optional, up to 40 characters). SSH addresses must exactly match the configured
administrator allowlist. Agent addresses must be empty. User and socket names use
`[A-Za-z0-9._-]{1,64}` and must not start with `-`. Unknown fields are rejected.
This endpoint does not accept credentials. It does not enroll an agent.

`Host` adds `id`, `state`, `statusReason`, `stale`, `createdAt`, `updatedAt`,
and nullable `observedAt`. State is the last explicit observation, not a live
transport guarantee. New profiles have no observation; Agent is pending, and
SSH needs local credential configuration. Old observations are marked stale.
Unreachable state never implies that a tmux process has stopped.

## SSH observation slice (T10–T11)

Host connection state is now derived from the last explicit observation. Listing
profiles never opens SSH connections. Initial SSH reason is `credentials_required`;
Agent remains `connector_pending`. `observedAt` is the last probe attempt, not
evidence that a cached inventory is current. SSH metadata and options are admin-only.

Configure SSH locally with `hub ssh-configure --host-id ID --key-file PATH
--host-key-file PATH --expected-fingerprint SHA256:... [--port 22]`. The public
host key file must contain one OpenSSH public key obtained through a trusted
channel. The explicit expected fingerprint must match; this command never
fetches/trusts a key from the network. Private keys must be unencrypted dedicated
keys in files accessible only to their owner. The hub copies the private key to
its private secret directory; SQLite stores an opaque reference and public pin.
Local `hub ssh-revoke --host-id ID` revokes configuration, removes the owned key
file and invalidates cached inventory. Neither command connects to the host.

Dial requires the profile address to remain in the administrator allowlist, and
every resolved IP must be in Tailscale's IPv4/IPv6 address space. The client dials
the verified IP directly (no second DNS lookup), verifies the pinned host key,
authenticates with the dedicated key, checks `id -un`, then runs only fixed
read-only tmux commands. Overall timeout: 10 seconds. At most four observations
globally and one per host; excess requests return 429. Stdout is limited to 1 MiB and stderr to 16 KiB per command.

Inventory has `hostId`, `socketId`, `transport`, `state`, `statusReason`,
`observedAt`, `stale`, `epoch`, `capabilities`, and nested sessions/windows/panes
with native IDs and revisions. A fresh empty inventory is valid when SSH works
but no tmux server exists (`epoch:""`, `serverRunning:false`). Inventory PTY capability remains false: it does not advertise conditional
experimental read-only eligibility. Terminal options and fresh per-viewer policy
checks govern that slice. Control/independent-pane capabilities remain false. Cached data
always retains its original `observedAt` and is marked `stale:true` after failure.
No stale snapshot is presented as live. With no cache, failures are sanitized
422 configuration/validation, 423 unreachable, 429 busy, or 503 degraded/unsupported.
No raw SSH/command stderr is returned or persisted. Probe failures are audited.

## Experimental session rename (T20, partial)

Disabled by default: `TMUX_MONITOR_MUTATIONS_ENABLED=true`. SSH/tmux3.8 rename
is the previously verified slice. Create/kill source additions below are untested;
Agent mutation parity remains unimplemented.
`GET /api/v1/hosts/{id}/session-options` requires tmux:read and returns
`{renameEnabled,canRename}`. Write requires tmux:read + tmux:write, login, exact
Origin and CSRF. `PATCH /api/v1/hosts/{id}/sessions/{sid}` accepts only
`{name,epoch,revision,confirmed:true}` and a random 32-hex `Idempotency-Key` header.
New names are 1–64 ASCII letters/digits/underscore/hyphen, first character not
hyphen. Native session ID is mandatory. Names affect all clients on that session.

Sessions expose an additional `renameRevision`: hash of server epoch and session
ID/name/creation time. Use it for this endpoint's `revision`; the existing tree
`revision` remains for observation and future layout mutations. Window/pane
activity does not invalidate a rename. A fresh SSH snapshot must match the epoch
and renameRevision. Immediately before rename, a non-yielding tmux `if-shell -F`
guard checks server pid/start/socket/version and session ID/creation/name on the
tmux command queue. No raw shell, kill-server, resize, or custom command input.
External rename/restart/removal produces conflict/not_found instead of retargeting
by name. Hash revisions cannot detect an external change away and back to the
identical state. External hooks run under the host operator's configuration.

SQLite migration004 durably reserves (actor, hashed key, request hash, operation
ID) and audits intent BEFORE remote execution. A fresh permission/credential check
runs immediately before dispatch. Revocation cannot undo an operation already
in flight. Requests are never retried automatically by hub or browser. The
idempotency request hash binds host, native ID, epoch/revision, name and current
credential reference. Same key/body returns its stored outcome after fresh access
checks; a different body/credential is 409 idempotency_conflict. Pending records
(concurrent request, lost reply, crashed hub) return 409 operation_uncertain and
NEVER execute again, including after restart. Records are retained without expiry,
maximum10000 globally; 429 operation_limit on exhaustion, with no automatic prune.
Do not delete records to retry an uncertain operation; verify inventory first.

200 `{operationId,state:"succeeded",sessionId}` confirms rename completed at the
time of execution; it is not a fresh inventory. Refresh explicitly after success.
400 malformed/unknown JSON, 409 conflict/duplicate_name/operation_uncertain,
404 not_found, 422 invalid_request
or tmux_unsupported, 429 busy/operation_limit, and existing SSH errors are sanitized.
Unknown SSH/write/timeout outcomes are operation_uncertain, without retry. Cache
is invalidated before dispatch; it is never used as mutation authority. Audit
contains actor/host/epoch/native target/result only, not names, key or request body.
Browser requires confirmation, clears drafts on close, and requires a fresh
inventory before another attempt after failure. Gate host/device tests remain open.

### Session create/kill additions — UNTESTED

Implemented source is not qualified: the user explicitly requested development
without testing. No test/build/browser validation or CI is claimed for this
addition. Both existing MUTATIONS_ENABLED and the separate
`TMUX_MONITOR_SESSION_LIFECYCLE_ENABLED=true` opt-in are required. Default false.
Session options add `{lifecycleEnabled,canCreate,canKill}` with current permissions.

`POST /api/v1/hosts/{id}/sessions` requires tmux:read + tmux:write, Origin, CSRF,
Idempotency-Key and `{name,epoch,revision,confirmed:true}`. Inventory adds
`createRevision` (`cr_...`): hash of the server epoch and sorted session identities,
names and creation times, excluding window/process activity. Create requires an
existing tmux3.8 server and a matching session set. No-server/empty epoch is
server_required; this endpoint never bootstraps a tmux server. The final `tmux -N`
guard checks epoch fingerprint and every session identity/name before detached
new-session, with initial120x40 geometry and the host's default shell. No custom
command, cwd, environment or socket override is accepted. Existing clients are
not selected/resized by the catalog. New name restrictions match rename.

`DELETE /api/v1/hosts/{id}/sessions/{sid}` requires tmux:read + tmux:kill,
Origin, CSRF, Idempotency-Key and `{epoch,revision,confirmation,confirmed:true}`.
Use the full session tree `revision`, not renameRevision. Confirmation must equal
the native session ID exactly. A fresh snapshot and final server guard cover
server/session identity/name and window/pane membership, names, indices, active
state, dimensions and current process command. Changes produce conflict. The
catalog issues only kill-session for that native ID, never kill-server. Killing
a session detaches its clients and can terminate processes in its unshared
windows; linked windows may remain in other sessions. UI displays that impact.

Loop guards are bounded to64 sessions/windows/panes per relevant collection and
64KiB serialized commands; larger targets return mutation_limit. These new loop
formats, last-session kill behavior and empty-server create remain untested.
Hash revisions retain the same ABA limitation. Host hooks may delay/alter state;
missing/ambiguous acknowledgement remains operation_uncertain, with no retry.

Create returns201, kill returns200 with `{operationId,state:"succeeded",sessionId}`.
Migration005 adds result_target metadata to the durable ledger for create replay.
The action is part of the request hash, so one key cannot be reused across
rename/create/kill. Same reservation/audit/cache-invalidation/10000-record policy
applies; pending survives restart and never dispatches again. Replays require
fresh permissions and current credential binding, without checking a now-deleted
kill target. Completion/result audit commit together. No terminal contents or
request names are persisted. Downgrade5→4 discards create result IDs and therefore
must not be used to recover/retry unknown operations. UI requires fresh inventory
after failure and never retries automatically. No change is made to runtime/.env.

## Experimental window rename (T21, source only)

`PATCH /api/v1/hosts/{id}/windows/{wid}` requires the mutations flag and
`TMUX_MONITOR_WINDOW_MUTATIONS_ENABLED=true`. The window flag defaults to false.
Session options expose `canRenameWindow` for callers with read and write access.
Login, exact Origin, CSRF and a 32-hex `Idempotency-Key` are required.

Send `{sessionId,name,epoch,revision,confirmed:true}` from fresh SSH inventory.
Use native session and window IDs and the revision of that window in the selected
session. The name follows the session rename character rules. This slice accepts
tmux 3.8 windows with a single link. Names must be unique within the session.
tmux disables automatic renaming for the renamed window.

Fresh inventory and the final tmux guard check the server, session, window and
pane state. The guard also checks for a new link or a duplicate sibling name.
Success returns 200 with `{operationId,state:"succeeded",windowId}`. The existing
operation ledger persists intent and outcome and revalidates SSH access before
dispatch. Pending or ambiguous results are reconciled through inventory. The
operation uses the current schema. Build, tests, browser checks and CI are pending.

## Experimental window creation (T21, source only)

`POST /api/v1/hosts/{id}/sessions/{sid}/windows` uses the same two flags, login,
Origin, CSRF, `tmux:read` and `tmux:write` permissions and 32-hex
`Idempotency-Key` as window rename. Session options expose `canCreateWindow`.
Use the native session ID and send `{name,epoch,revision,confirmed:true}` with
the selected session's tree revision from fresh SSH inventory. The name follows
the rename rules. Query parameters are rejected.

The target must be an existing ungrouped tmux 3.8 session with fewer than 64
windows. The connector validates the epoch, revision and name uniqueness from
fresh inventory. The final guard checks server and session identity, ungrouped
status, and the observed window IDs, indices and names. A change at this stage
returns a conflict. tmux allocates the index and starts its configured default
process with the new window detached. The new window is visible in the session's
window list. Host-configured tmux hooks can run as usual.

Success returns 201 with `{operationId,state:"succeeded",windowId}`. The
existing ledger retains the outcome and returned window ID without dispatching
again on replay. Inspect fresh inventory after an uncertain outcome. Build,
tests, browser checks and CI are pending.

## Experimental window removal and pane layout (T21, source only)

These SSH tmux 3.8 operations require both `TMUX_MONITOR_MUTATIONS_ENABLED`
and `TMUX_MONITOR_LAYOUT_MUTATIONS_ENABLED`. The layout flag defaults to false.
All requests require login, exact Origin, CSRF, `tmux:read`, a 32-hex
`Idempotency-Key`, and `confirmed:true`. Query parameters are rejected.

| Endpoint | Additional permission | Additional JSON fields | Success |
|---|---|---|---|
| `DELETE /api/v1/hosts/{id}/windows/{wid}` | `tmux:kill` | `sessionId`, `confirmation` equal to `wid` | 200 with `windowId` |
| `POST /api/v1/hosts/{id}/panes/{pid}/split` | `tmux:write` | `sessionId`, `windowId`, `direction` (`side-by-side` or `stacked`) | 201 with new `paneId` |
| `DELETE /api/v1/hosts/{id}/panes/{pid}` | `tmux:kill` | `sessionId`, `windowId`, `confirmation` equal to `pid` | 200 with `paneId` |

Send `epoch` and the containing window's `revision` from fresh inventory for
all three requests. IDs are native tmux IDs. Session options add `canKillWindow`,
`canSplitPane` and `canKillPane` as permission and feature indicators.

Targets must be single-link windows in an ungrouped session. The hub refuses
removal of the session's last window or the window's last pane and refuses pane
layout operations on a zoomed window. Split starts the tmux-configured default
process without selecting the new pane. Split and removal affect the shared
layout. Removing an active window or pane can change the active selection, and
removal can stop processes in the affected panes. Host tmux hooks may run.

The hub checks fresh inventory and uses a final tmux guard for target identity,
links, relevant counts and observed window/pane state. A missing target in fresh
inventory returns 404. Changes and scope restrictions return 409. Success
also includes `operationId` and `state:"succeeded"`. Replays use the stored
outcome and never redispatch. Inspect fresh inventory after an uncertain result.
No schema changes. Build, tests, browser verification and CI are pending.

## Experimental pane snapshot (T21, source only; untested)

`TMUX_MONITOR_PANE_SNAPSHOT_ENABLED` defaults to false and is independent of the
terminal/administrative mutation flags. `GET /api/v1/terminal/options` adds
`paneSnapshotEnabled`. The current implementation targets SSH with tmux3.8.

`POST /api/v1/hosts/{id}/panes/{pid}/snapshot` accepts `{epoch,revision}` from
fresh inventory (`pane.revision`, not window/session revision). `pid` must be a
native `%N` ID. This POST is a one-shot read action; it uses the existing Origin
and CSRF checks in addition to login and `tmux:read`. No caller-defined command,
history range, socket, or output format is accepted. Query parameters are rejected.

The connector reuses SSH pin/address/user checks, the shared observation gate
(4 global / 1 per host) and 10-second deadline. It reads inventory on the same
connection and compares epoch and pane revision. A fixed `if-shell -F` guard
rechecks server fingerprint and pane/window identity, active flag, dimensions
and current command just before `capture-pane -p -S -100`. No active pane is
selected, no resize/attach occurs, and no tmux paste buffer is created. The
capture is the visible pane plus up to100 preceding lines; it is best-effort
text, not a reconstruction of a full-screen terminal or a live stream.

200 returns `{paneId,capturedAt,text,truncated}`. The serialized guard command
is capped at64KiB. Raw stdout is capped at256KiB
including its protocol marker; overflow fails without returning partial output.
The result retains the most recent64KiB at UTF-8 boundaries after sanitization;
`truncated` reports byte clipping, not whether older history exists. The
browser renders plain text only and discards it on close, pagehide or a new
capture. No automatic capture, polling or reconnect is performed.

ACL/login/credential reference are revalidated before capture and again before
the response. Metadata-only audit records intent and outcome; failure to record
either prevents delivery. The text is never put into inventory cache, SQLite,
logs, or browser persistence. Responses use `Cache-Control: no-store`. Target
change returns409, missing/inaccessible target404, disabled/over-limit503,
unsupported/invalid422 and busy429. No stale snapshot fallback is used.

Source only: build, tests, browser verification and CI are deferred at the user's
request. Agent parity remains future work.

## Experimental SSH terminal (T12, partial)

Disabled by default: operator must set `TMUX_MONITOR_TERMINAL_ENABLED=true`.
This is a development slice, not completion of the P0 access/device gates.
SSH session viewers start read-only. Interactive activation is described below;
viewport resize remains rejected. No automatic reconnect or input replay. All requests require login.

`GET /api/v1/terminal/options` returns `{enabled,mode:"read_only",paneSnapshotEnabled}`.
`POST /api/v1/terminal/tickets` requires exact Origin, REST CSRF and `tmux:read`.
Body: `{hostId,sessionId,epoch}` (native `$N` session ID). Response:
`{ticket,expiresIn:30}`. The random ticket is stored hashed, usable once, bound to
the login token, user, host, socket, credential reference, epoch and target.
Maximum 64 pending tickets globally / 8 per login. No token in URLs or logs.

Browser upgrades `/ws/v1/terminal` with cookie, exact Origin and subprotocols
`["tmux.v1","ticket.<ticket>"]` for legacy clients; the current browser uses
`tmux.v2` as described below. The server selects the version, never the ticket. Upgrade consumes
the ticket, rechecks authorization and reserves a viewer (8 global / 4 per user /
4 per host). Unsupported/missing protocols are rejected. No REST CSRF header is
needed on upgrade: the one-use ticket was issued by a CSRF-protected POST.

The connector freshly verifies the pinned SSH host, OS user, tmux server epoch
and session. Requires tmux >=3.7, global default `window-size manual` and every
window in the selected session effectively `manual`. The application never
changes remote options. The fixed attach catalog captures its SSH PTY identity
in a NUL-terminated metadata frame, then waits for the connector's fixed initialization
ack before starting tmux (avoiding startup output flushes). The connector consumes that frame and verifies that exact tmux client
remains on the selected native session. Client switch or loss closes the viewer
on its next policy check. This metadata is not forwarded as terminal output. Otherwise it reports `terminal_size_policy` and does not
attach. The PTY uses the active remote window size plus its status rows (maximum
500 columns / 205 rows); it does not follow browser dimensions. Attach uses
`read-only,ignore-size`. Policy/target/epoch and login/ACL/credential reference
are rechecked every 2 seconds; changes close the viewer. An operator changing
remote options during viewing can affect tmux before the next check.

`terminal.opened` JSON contains `viewerId` (32 hex digits), `mode:"read_only"`,
`cols`, `rows`, `generation:1`, `sequence:0`. Target is bound at ticket issue;
there is no second `terminal.open` message. Each binary output frame has a
30-byte header: version uint8=1, direction uint8=0 (server output), generation
uint32BE=1, sequence uint64BE starting at 1, viewer ID raw 16 bytes; then PTY bytes.
Chunks <=32 KiB; incoming message limit 64 KiB. Read-only binary input, in-band mode changes and
resize requests close with `input_forbidden` (no browser input sent to SSH stdin).
Read-only accepts only `{"type":"terminal.detach"}` from the client;
interactive binary frames follow the activation contract below.

`terminal.closed` contains `reason`; `error` contains sanitized `code`;
`resync_required` asks for a fresh viewer after backpressure. Queue maximum
1 MiB per viewer, write deadline 2 seconds, viewer lifetime 30 minutes. Closing
only detaches the SSH client. No terminal contents are cached or audited.
Audit open/close/denial records include host, epoch/native target and reason.
The browser disables stdin in read-only, OSC52 clipboard, window manipulation and automatic
link activation; xterm write backlog is capped. Manual reopening gets a new
ticket, viewer ID and empty renderer, starting in read-only/generation 1.

### Connection liveness (T13, partial)

The current browser requests subprotocol `tmux.v2` plus `ticket.<ticket>`.
The server also accepts legacy `tmux.v1`, preserving its existing message set;
v1 receives no heartbeat JSON. Authentication, tickets, input/output binary header
version 1, limits and mode transitions are unchanged. Deploy the rebuilt hub with
the current web assets; older hubs do not support v2.

After `terminal.opened`, v2 sends WebSocket ping every 5 seconds, awaiting pong
for at most 5 seconds. A missing pong detaches only this viewer with
`heartbeat_timeout`. After a successful ping/pong the writer sends
`{type:"terminal.heartbeat",viewerId,generation:1}`. It carries no terminal data,
does not advance either binary sequence, and never writes to SSH stdin. Idle
terminals are healthy; output activity is not required for liveness.

The browser allows 15 seconds for WebSocket connection/setup and subsequently
15 seconds without a valid opened/heartbeat. Deadlines are checked before input,
on incoming messages, every second and on visibility return. Expired connections
cannot be revived by queued messages after sleep. Offline or pagehide closes the
viewer immediately; online/pageshow never reactivate input or replay it. The first
terminal reason is retained; later close/error/messages cannot overwrite/revive
it. Pending activation/paste/modifiers are discarded. Buka ulang is an explicit
action issuing a new read-only ticket, fresh renderer and sequence namespace.
In-flight input may already have reached the host; no undo is promised. Timers
can be suspended by the OS, so detection occurs when execution resumes; real
network-switch/device qualification remains open.

### Explicit interactive activation

Every ordinary `/terminal/tickets` request still creates **read_only**. It does
not accept a mode field. `terminal.opened` additionally contains `canWrite` and
`mode` (`read_only` or `interactive`). Interactive remains behind the existing
operator terminal feature flag and the same sizing/version policy.

`POST /api/v1/terminal/viewers/{viewerId}/mode-tickets` accepts `{mode}` with
`interactive` or `read_only`, requires exact Origin + REST CSRF, an active viewer
owned by the same login token, fresh `tmux:read`, and **terminal:write** for
interactive. It records the requested mode, closes that viewer and waits for
its SSH/client cleanup, then returns `{ticket,expiresIn:15}`. Unsupported, same-mode
and concurrent transitions are rejected. The ticket is one-use, hashed, bound to
the same target/epoch/socket/credential/login and requested mode. There is one
transition per viewer. Failed/ambiguous transitions never replay input.

The browser explicitly upgrades with this ticket to a **new viewer ID**, empty
renderer and generation 1. Read-only uses the existing fixed attach command;
interactive attaches a separate client with **ignore-size**, without read-only.
The application never toggles flags of another tmux client. Failure to open a
replacement leaves the old viewer detached. Generic reopen/reconnect always uses
a new ordinary read-only ticket. In-band `terminal.set_mode` and resize messages
remain rejected; the mode changes only through the CSRF-protected REST flow.

Interactive binary input uses the same 30-byte header, direction=1, generation=1,
that connection's viewer ID, and a separate strictly increasing input sequence
starting at 1. Payload 1–16384 bytes, queue <=8 frames (128 KiB), token bucket
64 KiB/s with 32 KiB burst. Header/generation/sequence mismatch, readonly input,
overflow/rate limit, revoked access or failed write closes the viewer. Each frame
checks the current login/read/write ACL and credential reference before writing;
SSH writes have a 2-second deadline and no retry/replay. Policy/epoch checks also
continue periodically on the bound SSH connection. Input can include UTF-8 and
control bytes. No input content is logged or audited.

UI activation requires a deliberate confirmation for that viewer and displays
the shared-session impact. Keyboard and small control-key buttons work only in
interactive mode. Paste is capped at 16 KiB and multiline paste requires a review
and explicit confirmation on every host. Pending paste/input is dropped when the
connection/mode changes. OSC52, automatic links and window operations stay disabled.

### Touch keyboard controls (T31, partial)

The toolbar is active only in a confirmed interactive viewer. Ctrl/Alt/Shift are
one-shot modifiers for toolbar keys and its single-character combination field;
they do not rewrite xterm keyboard, IME, paste or terminal-response events.
Successful sends clear the modifiers and draft. Close, mode transition, reconnect
and target changes reset toolbar drafts/modifiers; no input is persisted/replayed.
Read-only never offers a usable toolbar, and the gateway checks remain authoritative.
Unsupported character combinations show an error without sending bytes. Cursor
keys respect xterm's application cursor mode and legacy xterm modifier encoding.

The prefix selector defaults to Ctrl+B and supports single control-key prefixes.
It sends only the chosen prefix byte, with no following tmux command. Selection
is kept in memory for the current target view, including mode replacement, and
resets when that view closes or host/session/epoch changes. It never changes the
remote tmux configuration. No localStorage or API endpoint is added. Touch
controls retain 44px targets and explicit labels/pressed states. Physical device
keyboard/IME qualification remains a release gate.

New reasons include `credentials_required`, `credentials_invalid`,
`address_not_allowed`, `address_not_tailnet`, `host_key_mismatch`,
`authentication_failed`, `timeout`, `connection_failed`, `os_user_mismatch`,
`tmux_missing`, `inventory_invalid`, `inventory_changed`, `output_limit`,
`agent_unavailable`. An SSH connection failure never means a tmux process died.
Terminal startup can also report `terminal_tty_unavailable` (missing/incomplete
metadata frame) or `terminal_tty_invalid` (unrecognized PTY identity); neither
includes remote output or paths in the error response.

`AuditEvent` contains `id`, `actor`, `action`, optional `hostId` and `target`, `result`,
`requestId`, and `at`. Audit metadata never includes passwords, session tokens,
credentials, terminal input/output, or raw HTTP request bodies. Administrative
host changes and their success audit record commit in the same transaction.

Errors: 400 malformed JSON, 401 unauthenticated, 403 forbidden/CSRF/Origin,
404 absent or inaccessible target, 405 method not allowed, 422 validation,
429 rate limit, 503 unavailable, 500 internal error. Unknown API/WS endpoints
require login before returning JSON 404. Terminal upgrades follow the experimental
contract above and are disabled unless explicitly enabled by the operator.
